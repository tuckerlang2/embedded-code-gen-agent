# Rover control software

Two-board yard-monitoring rover: ESP32 DevKitC V4 (real-time I/O
co-processor) + Raspberry Pi Zero 2 W (compute/storage/networking),
linked over USB serial. This code is hand-written and reviewed, not
generated by the agent in `src/` — see CLAUDE.md's "Open decisions" note
for why: the agent currently models one spec -> one board -> one file,
and this project needs two boards that agree on a shared serial
protocol, which isn't something to hand to an LLM per-side independently.

## Layout
```
rover/
  PROTOCOL.md              - the Pi<->ESP32 wire protocol. Read this first.
  wiring_diagram.md         - 4WD/dual-Sabertooth wiring block diagram.
  esp32_firmware/
    esp32_firmware.ino      - ESP32 firmware: drive relay (now to TWO
                               Sabertooths, front+rear axle, as of the
                               2026-11-19 4WD conversion), watchdog, soil
                               probe, servo. Last confirmed compile/flash
                               was on the pre-4WD, single-Sabertooth
                               version (user-verified 2026-10-04) — the
                               4WD firmware change has NOT yet been
                               compiled or flashed on real hardware.
  pi/
    protocol.py              - frame encode/decode, shared by drive_controller.py
    drive_controller.py       - gamepad -> serial drive loop
    camera_stream.py          - live MJPEG stream for phone FPV viewing (view-only,
                                 no interaction with drive_controller.py or the ESP32 link)
    test_protocol.py          - unit tests for protocol.py (passing)
    requirements.txt
```

## Status as of 2026-11-19 — 4WD / dual-Sabertooth conversion
- **Drivetrain converted from 2WD to 4WD skid-steer, second Sabertooth
  2x12 now in hand.** No native 4-channel driver exists in this power
  class (checked the Sabertooth line and Basicmicro RoboClaw — both
  dual-channel only), so the standard approach applies: one Sabertooth
  per axle, FRONT (existing unit, Serial2/GPIO17) and REAR (new unit,
  remapped Serial1/GPIO19 TX). Both axles get identical left/right
  speed commands every frame, which is what keeps zero-turn working and
  is why `PROTOCOL.md`'s frame format needed no change. Firmware updated
  in `esp32_firmware.ino`; see `wiring_diagram.md` for the wiring.
  **NOT YET compiled, flashed, or run on real hardware** — this is a
  code/doc update only, done ahead of the physical rewiring.
- **Resolved (2026-11-19, user-confirmed):** the hardware E-stop relay's
  cut covers BOTH Sabertooths' power feed. The REAR unit's DIP switches
  are set identically to the FRONT unit's. Note what this does and
  doesn't settle: it rules out the E-stop-only-covers-one-unit failure
  mode, and it means the two units won't disagree with each other — it
  does NOT independently confirm that the shared DIP configuration
  actually matches the firmware's `SABERTOOTH_BAUD` (9600, simplified
  serial) assumption, since the FRONT unit's switches were never read
  off and checked against that assumption in the first place (see
  "Before this drives real motors" below — still open, now a single
  shared item instead of two separate ones).
- Protocol designed and documented (`PROTOCOL.md`).
- ESP32 firmware (pre-4WD, single-Sabertooth version): compiled and
  flashed clean on real hardware (Arduino IDE, ESP32 Dev Module board
  selection, esp32:esp32 core + ESP32Servo library). Runtime confirmed
  working: ESP32 boots clean and sends valid telemetry. (Earlier hit a
  boot loop from a bad/corrupted flash image — fixed by a full erase +
  reflash. See PROGRESS.md Session 6.)
- Pi-side `protocol.py` has real unit test coverage, run and passing
  (`python3 test_protocol.py` or `pytest`).
- `drive_controller.py`: **motors confirmed driving from the gamepad for
  the first time** (2026-10-10). `TURN_AXIS` was fixed (was reading the
  left trigger, not the right stick — see PROGRESS.md Session 6 for the
  full debugging trail covering a flaky USB hub, a bad cable, a corrupted
  git clone, and the ESP32 boot loop, all encountered along the way).
- **NOT yet done: the watchdog bench test** (wheels off the ground, unplug
  the Pi<->ESP32 link mid-drive, confirm motors stop within ~400ms on
  their own). This is the next required step before any unsupervised
  driving — see "Before this drives real motors" below.
- Known issue, not yet fixed: the Pi's USB hub is likely underpowered —
  the gamepad showed USB errors (`usb_submit_urb failed`) in `dmesg`
  consistent with current starvation when driving keyboard+mouse+
  controller+ESP32 simultaneously off a bus-powered hub. A powered hub
  (own power supply) is recommended before relying on this for real use.
- Camera: `camera_stream.py` running on real hardware (Pi Camera Module 3
  / IMX708, MJPEG over HTTP, viewable in a phone browser at
  `http://<pi-ip>:8080/`). Mounted upside-down to route the CSI cable --
  use `--flip` (on by default in `rover-camera.service`) so the stream
  displays right-side up. **Known gap, not yet fixed:** the capture
  pipeline can silently stall mid-stream (libcamera logs "Camera frontend
  has timed out") while systemd still reports the service as "active" --
  root cause not conclusively isolated (ruled out: resource conflict, CMA
  memory, Pi undervoltage; suspected but unconfirmed: cable strain from
  the upside-down mount). If the stream goes dark without the service
  restarting, this is why -- `sudo systemctl restart rover-camera.service`
  is the workaround for now. See "Camera: FPV phone viewing" below and
  PROGRESS.md Session 9 for the full diagnostic trail.
- Not yet built: GPS/route planning (explicitly deferred, per the
  project's scope decisions), phone UI for drive control (gamepad is the
  chosen input for now -- see PROGRESS.md).
- See "Deferred scope" section below for obstacle sensors/LEDs/limit
  switches — explicitly not being built yet, noted for later.

## Running the Pi side
Manually, for testing:
```bash
cd rover/pi
pip install -r requirements.txt
python3 drive_controller.py --port /dev/ttyUSB0   # adjust port as needed
```

### Auto-start on boot (systemd)
`rover-drive.service` runs `drive_controller.py` automatically at boot and
restarts it if it exits (e.g. the ESP32 hadn't enumerated as `/dev/ttyUSB0`
yet at boot time -- it'll keep retrying every 5s). Install it once:
```bash
sudo cp rover-drive.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rover-drive.service
```
Check it's running and watch its logs:
```bash
sudo systemctl status rover-drive.service
journalctl -u rover-drive.service -f
```
Stop/disable it (e.g. to go back to running it manually for debugging):
```bash
sudo systemctl stop rover-drive.service
sudo systemctl disable rover-drive.service
```
The service file hardcodes the `bighonker` user and the repo path under
their home directory -- edit `User=` and the paths in
`rover-drive.service` if either ever changes, then `daemon-reload` again.
Check `ls /dev/tty*` after plugging in the ESP32 to find its actual
device name — it may enumerate as `/dev/ttyUSB0` or `/dev/ttyACM0`
depending on the specific board's USB-serial chip.

Gamepad axis indices in `drive_controller.py` (`THROTTLE_AXIS`,
`TURN_AXIS`) assume a typical Xbox-layout controller on Linux. The
script prints the connected controller's name/axis count/button count
at startup — if driving feels wrong (e.g. turning does nothing, or the
wrong stick drives), check that printout against the constants and
adjust.

## Camera: FPV phone viewing
Pi Camera Module 3 (Standard, IMX708, autofocus) connected to the Pi's CSI
ribbon port. `camera_stream.py` serves a live MJPEG feed for viewing in a
phone browser while driving with the gamepad -- flying it "like a drone,"
phone for eyes, controller for hands. **View-only**: it has no connection
to `drive_controller.py`, `protocol.py`, or the ESP32 link, and losing the
video feed does not affect drive safety (the ESP32's watchdog, per
PROTOCOL.md, is independent of this).

Setup (one-time):
```bash
sudo apt install -y python3-picamera2
# picamera2 is a system package tied to libcamera -- installed via apt,
# not pip, and not in requirements.txt / the venv for this reason.
```
Enable the camera interface if not already on (`sudo raspi-config` ->
Interface Options -> Camera, or it may be auto-detected on recent
Raspberry Pi OS with no explicit enable step needed -- check
`libcamera-hello --list-cameras` to confirm the Pi sees it before
troubleshooting the stream itself).

Manually, for testing:
```bash
cd rover/pi
python3 camera_stream.py --port 8080
```
Then on your phone, same WiFi network as the Pi, go to `http://<pi-ip>:8080/`.

Auto-start on boot, same pattern as `rover-drive.service`:
```bash
sudo cp rover-camera.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rover-camera.service
```

**Not yet tuned:** default is 640x480 to keep latency low over the Pi
Zero 2 W's WiFi for FPV-style driving -- raise resolution/bitrate
(`--width`/`--height`/`--bitrate`) only after confirming the lower
setting's actual latency is acceptable to you in practice; this hasn't
been measured on real hardware yet. If the Pi's WiFi is shared with
anything else driving to/from it, expect that to compete for the same
bandwidth.

**Known gap, accepted for this prototype (2026-10-22):** the watchdog
bench test (see "Before this drives real motors" below) has NOT been
done. User's explicit call: this build is for an investor demo, not
unsupervised field use, and the watchdog test is being skipped for now
rather than gating the demo. Revisit before any driving beyond a
controlled demo setting.

## Flashing the ESP32 side
1. Install the `esp32:esp32` arduino-cli core and the `ESP32Servo`
   library (see comments at the top of `esp32_firmware.ino`).
2. Compile and verify clean: `arduino-cli compile --fqbn esp32:esp32:esp32 esp32_firmware/`
3. Review the compiled output and the source against
   `hardware_reference/esp32_devkitc_v4.md` before flashing — per this
   project's non-negotiable human-review-before-flash rule.
4. Flash: `arduino-cli upload -p <port> --fqbn esp32:esp32:esp32 esp32_firmware/`

## Deferred scope: obstacle detection + status LEDs + probe limit switches
(Added 2026-10-04. Explicitly NOT built now — this is a note for later,
after mechanical assembly and basic manual-drive operation are working.
Revisit once there's appetite to scale from manual driving toward more
autonomous/route-based operation — this is additive to that, not to the
current "short mowed grass, no obstacle handling" scope.)

Planned additions: 3x ultrasonic distance sensors (front/left/right),
3x status LEDs, 2x limit switches for the soil probe's extend/retract
travel.

**Voltage warning, confirm before wiring:** classic HC-SR04-style
ultrasonic sensors run on 5V and their ECHO pin outputs a 5V signal — the
ESP32 is 3.3V-only and NOT 5V tolerant. Either use a 3.3V-native
ultrasonic module, or put a voltage divider on each ECHO line. Don't
wire ECHO straight to a GPIO.

**Scope question to resolve before building, not after:** are the
ultrasonic sensors for passive logging/awareness, or active obstacle
avoidance (rover stops/reroutes on detection)? The latter is real
decision-logic, not just a sensor read — reopens the "no obstacle
handling" scope decision deliberately, rather than accidentally.

**Pin budget already worked out** (not yet in the firmware), chosen to
avoid flash pins (6-11), use input-only pins (34/35/36/39) for ECHO
lines since ECHO is a pure input anyway, and keep I2C (21/22) free for
a future GPS/sensor module:

| Function | Pin |
|---|---|
| Ultrasonic 1 (front) TRIG / ECHO | GPIO4 / GPIO36 |
| Ultrasonic 2 (left) TRIG / ECHO | GPIO14 / GPIO39 |
| Ultrasonic 3 (right) TRIG / ECHO | GPIO18 / GPIO35 |
| Status LED 1 | GPIO2 (shares the DevKitC's onboard LED) |
| Status LED 2 | GPIO15 (strapping pin — brief boot flicker possible, fine for a non-critical LED) |
| Status LED 3 | GPIO23 |
| Probe extend limit switch | GPIO25 |
| Probe retract limit switch | GPIO26 |

11 new pins + the 8 already in use (Pi link, FRONT + REAR Sabertooth
links, soil ADC, servo — GPIO19/27 were consumed by the REAR Sabertooth
in the 2026-11-19 4WD conversion and are no longer free) = 19 of 32
broken-out GPIO. GPIO21/22 (I2C), 0, 5, 12, 32, 33 stay free as margin.

Assumed "extend/retract sensors" = two binary limit switches (mechanical
end-stops), not continuous position feedback. If continuous position is
actually wanted later, that's a different sensor (e.g. a potentiometer)
on an analog pin, not a digital input — confirm which before wiring.
